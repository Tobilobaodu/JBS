# First Sprint Tasks

Ticket-sized breakdown of Phase 1 (Foundations) so a developer can start immediately. Each task lists what "done" looks like — use these as literal ticket descriptions if helpful.

## Sprint 1: project setup and auth

- [ ] **Repo and environment scaffolding.** API service skeleton (Python/FastAPI, per `01-implementation-plan.md` §2), local dev environment via Docker Compose (API + PostgreSQL + Redis + queue emulator), `.env.example` with all required config keys documented, secrets never committed. *Done when:* a fresh clone can run the API locally with one setup command.
- [ ] **Database and migration tooling.** Set up a migration framework, create initial migration for `users` and `user_sessions` per `03-data-model.md`. *Done when:* migrations run cleanly on a fresh database and are reversible.
- [ ] **`POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`.** Implement per `05-openapi.yaml`. Password hashing, session/token issuance, auth middleware for all subsequent protected routes. *Done when:* schema-validated against the OpenAPI spec, and a protected route rejects unauthenticated requests with a proper error shape.
- [ ] **Object storage integration.** S3-compatible bucket setup, upload/retrieve helper functions, encryption at rest confirmed. *Done when:* a file can be written and read back via the storage abstraction, not directly via SDK calls scattered through the codebase.
- [ ] **Secrets management setup.** Wire up the secrets vault (whatever's chosen for the environment) for API keys, DB credentials, storage tokens. *Done when:* no secret exists in code, `.env` files in version control, or CI config in plaintext.

## Sprint 2: CV upload and processing job scaffolding

- [ ] **`cv_files` and `processing_jobs` tables.** Migrations per `03-data-model.md`. *Done when:* both tables exist with correct FKs and the status enums match `05-openapi.yaml`.
- [ ] **`POST /cvs` — upload endpoint.** Multipart file upload, validate type by content inspection (magic bytes, not just declared `Content-Type` — see `10-security-plan.md` §2) and size, store original file under a generated non-guessable storage key (never derived from the client filename), create `cv_files` row, create a `processing_jobs` row (`job_type: docling_extract`), enqueue the job, return `202` with `cvId` and `processingJobId` per the OpenAPI spec. *Done when:* invalid file types/sizes return `400`/`413`/`415` with a clear message; valid uploads return `202` and the file is retrievable from storage; a path-traversal filename doesn't affect the storage key.
- [ ] **Malware scanning on upload — blocking task.** Integrate a malware scanner (e.g. ClamAV or a managed equivalent) into the upload path, running before a file reaches the Docling/Textract pipeline. *Done when:* a known-bad test file (EICAR test file) is rejected, and a clean file passes through normally. This task doesn't currently exist in this sprint plan by default — flagged as a blocking gap in `10-security-plan.md` §2 and §13, and added here explicitly because `POST /cvs` should not take real traffic without it.
- [ ] **`GET /cvs`, `GET /cvs/{cvId}`, `DELETE /cvs/{cvId}`.** Standard CRUD scoped to the authenticated user. *Done when:* a user cannot retrieve or delete another user's CV (write a test for this specifically — see the IDOR test pattern in `10-security-plan.md` §3, which applies to every ID-scoped endpoint built from here on, not just this one).
- [ ] **`GET /jobs/{jobId}` — processing job status.** *Done when:* returns current status/retry count/last error per the `ProcessingJob` schema.
- [ ] **Queue setup and worker scaffolding.** Stand up the queue, create a base worker process structure that can pick up jobs by `job_type`, with retry/backoff and dead-letter handling. *Done when:* a test job can be enqueued and consumed end to end, including a forced-failure test that lands in the dead-letter path.

## Sprint 3: extraction pipeline

- [ ] **Docling worker.** Consumes `docling_extract` jobs, reads file from storage, runs Docling extraction, writes result to `cv_extraction_passes` (`pass_type: docling`), enqueues `textract_extract` job on success. Implement against the `DocumentParser` interface defined in `02-architecture-overview.md` §4a *before* writing Docling-specific code, not after — the interface boundary is the point of this task, not an afterthought. Deploy per the container base/CPU/memory spec in the same section, with no outbound network access at runtime. *Done when:* a digital PDF and a DOCX file both produce a stored extraction pass with populated text and metadata, the Docling-specific logic is fully contained behind the interface (verify by checking the merge/validation worker's code has no Docling-specific imports or type references), **and `confidence_score` reflects genuine parse quality, not a placeholder heuristic** — verify this specifically by feeding a deliberately garbled or badly-formatted test document through Docling and confirming the score actually drops relative to a clean CV, rather than staying high because a length-based or completion-based proxy was used instead of a real quality signal. This last check is a named, priority item because a plausible-looking but wrong confidence value passed code review and testing once already during this project's own implementation, and it silently broke the merge layer's "highest confidence wins" logic without any visible error — see `02-architecture-overview.md` §4 for the full account.
- [ ] **Textract worker.** Consumes `textract_extract` jobs, reads the same file from storage, calls Amazon Textract, writes result to `cv_extraction_passes` (`pass_type: textract`), enqueues `merge_parse` job on success. *Done when:* an extraction pass row exists for both a digital and a scanned/image-based test document.
- [ ] **Merge and structural validation worker.** Consumes `merge_parse` jobs, reads both passes, runs the structural validation checks described in `02-architecture-overview.md` §4 (section count, heading alignment, reading order, date consistency, bullet preservation, line coverage), produces the canonical `cv_raw_text` row with `structural_validation_result` populated, updates `cv_files.processing_status`. *Done when:* a deliberately mangled test CV (e.g. a two-column layout) produces `anomalyDetected: true` with a populated `anomalyDetail`, and a clean single-column CV produces `anomalyDetected: false`.
- [ ] **`GET /cvs/{cvId}/raw-text` and `GET /cvs/{cvId}/extraction-detail`.** Implement per the OpenAPI spec. *Done when:* both endpoints return real data for a fully processed CV and a proper `404`/appropriate pending-status response for one still in progress.
- [ ] **`POST /cvs/{cvId}/reprocess`.** Re-enqueues the pipeline from the Docling step. *Done when:* calling it on a previously processed CV creates new extraction pass rows rather than overwriting existing ones.

## Sprint 4: observability and Phase 1 close-out

- [ ] **Structured logging across all workers and the API.** Every job transition (queued → processing → completed/failed) logged with correlation IDs. *Done when:* a single `processing_jobs.id` can be traced through logs across all three workers involved in extraction.
- [ ] **Basic metrics.** Job throughput, failure rate, processing duration per job type, at minimum. *Done when:* dashboards or equivalent exist showing these for the extraction pipeline.
- [ ] **Error handling audit.** Walk every failure path in the extraction pipeline (bad file, Docling failure, Textract failure, timeout) and confirm each produces a meaningful `processing_jobs.last_error`, not a generic "something went wrong." *Done when:* each failure mode has been manually triggered and verified.
- [ ] **Phase 1 demo.** Upload a CV via the API, show it moving through `queued → extracting → merging → completed` status, retrieve the canonical text and extraction detail. This is the Phase 1 acceptance demo referenced in `01-implementation-plan.md`.

## Notes for whoever picks this up

- Don't build the CV parser/normaliser (structured profile extraction) in this sprint set — that's Phase 2, and it depends on the canonical extraction result being reliable first. Resist the urge to jump ahead; the merge/validation step is worth getting right before building on top of it.
- Test files: get a small set of representative CVs early — at minimum one clean single-column digital PDF, one DOCX, one scanned/image-based PDF, and one deliberately awkward layout (two-column or heavy table use). The structural validation logic is only as good as what it's been tested against.
- If Amazon Textract account/credentials aren't provisioned yet, that's a blocker to flag immediately, not something to work around with a stub that gets forgotten — the two-pass design in `02-architecture-overview.md` is a core product decision, not an optional enhancement.
- Read `10-security-plan.md` §2 before building the Docling/Textract workers — they should run sandboxed (resource-limited, no outbound network beyond what Textract's SDK needs) from the start, since retrofitting isolation onto a worker that already assumes broad access is a much bigger job than building it in from Sprint 3.
- When Phase 2 starts job post URL ingestion (`POST /job-posts/url`), read `10-security-plan.md` §4 before writing the fetch logic — a naive "fetch whatever URL the user gives us" implementation is a direct path to cloud credential theft (SSRF). This isn't a Phase 1 task, but it's worth knowing about now since it shapes how the fetch worker's network isolation should be planned alongside the extraction workers being built in this sprint.

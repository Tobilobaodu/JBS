# Product Extensions

Six ideas evaluated against one question: does this genuinely make the tool better at its actual job, or is it feature padding? Three are designed in enough detail to build now (#1–#3); two are real, deliberate schema extensions that support a later capability without committing to building it yet (#4–#5); one is flagged as a real opportunity that needs a separate go/no-go conversation before any design work, because it's the one idea here with a real fabrication-risk profile of its own (#6).

None of these are required for the core product this pack already specifies — a user can upload a CV, get a tailored draft, and get a cover letter without any of the six. They're differentiation on top of a working core, not prerequisites to shipping one.

---

## 1. ATS structural validation (build now)

### The gap this closes
The very first document that kicked off this whole project was about how ATS systems parse CVs to match them against job posts. Everything built since then matches *content* — does the CV's evidence support the job post's requirements. Nothing in the pack today checks whether a real-world ATS can even parse the document's *structure* well enough to extract that content in the first place. A CV can be perfectly evidence-matched by this system and still score zero at a real employer because their ATS choked on a two-column layout, text embedded in an image, or contact information in a header/footer their parser doesn't read. This is a different failure mode from anything currently tested, and it's arguably the most directly useful thing this tool could tell a user, because it's the one problem a job seeker has no way to self-diagnose.

### What it checks
A rules-based composite score (not a single AI call — this is deliberately not a generation surface, see the design note at the end of this section) run against the canonical merged extraction result (`cv_raw_text`) and the structured profile (`cv_profile_versions`):

| Check | What it looks for | Severity |
|---|---|---|
| Text-in-image detection | Content that only appears in the Textract OCR pass and not in Docling's native text extraction, on a document that isn't a scanned original — a strong signal that content is baked into an image rather than being real, selectable text | High |
| Multi-column / table-based layout | Layout structures that stress reading order (already flagged by `cv_raw_text.structural_validation_result.readingOrderConsistent`) — reuse that existing check as one input here rather than reimplementing it | Medium–High depending on severity |
| Contact info parseable location | Name, email, phone found in a conventional top-of-document position versus buried in a header/footer/text box that many ATS parsers skip entirely | High — flagged separately as `contact_info_parseable` on the table, since this is close to an automatic-reject condition on its own |
| Non-standard characters/fonts | Unicode characters, symbols-as-bullets, or decorative fonts that can render as garbage or get dropped by less capable parsers | Low–Medium |
| Section heading recognizability | Whether headings map to a canonical section per the mapping table already defined in `03-data-model.md` (§ on `cv_experience_items` etc.) — if this system's own parser needed a fallback to `unknown` for a heading, a stricter ATS parser likely will too | Medium |
| File format signals | DOCX-with-embedded-objects, PDF generated by an unusual tool chain (some page-layout software produces PDFs that extract poorly despite looking fine visually) | Low–Medium |

### Output
`ats_readiness_checks.overall_score` (0–1) plus the itemised `checks` array — surfaced to the user alongside the match score, not folded into it, since these measure genuinely different things (will this be read at all, versus how well does it fit this specific role) and conflating them would make the score harder to act on, not easier.

### Design note: why this stays a rules-based check, not a new generation call
Every other analysis surface in this pack (matching, tailoring, cover letters) goes through an LLM with schema validation and evidence binding, because those tasks involve genuine judgment about relevance and phrasing. ATS-parsing-hostility is different — it's closer to a linting problem than a judgment problem: known, enumerable patterns that are empirically hard for parsers, checked deterministically. Keeping it rules-based means no new prompt-injection surface (§5 of `10-security-plan.md` doesn't need to expand to cover this), no new LLM cost per check, and no risk of the non-fabrication guarantee needing to be re-proven for a new generation surface. If a future version wants an LLM to explain *why* a check failed in more natural language, that's a safe, low-risk addition on top of a deterministic score — don't build it the other way around (LLM decides the score, rules explain it), since that inverts where the risk sits.

### Phase placement
Phase 3 (matching and tailored CV drafting) is the natural home — it's a sibling analysis to matching, consuming the same canonical profile, and belongs in the same phase rather than bolted on later. Add as a distinct task, not folded into the existing matching-engine task, since it has no dependency on job post data at all (it only needs the CV) and could technically start as soon as Phase 2's parsing is done, if a team wants to build it earlier for parallelism.

### New endpoint
`POST /cvs/{cvId}/ats-check` → `202`, creates an `ats_readiness_checks` row via a `processing_jobs` entry (`job_type: ats_check`), consistent with every other async pattern in this pack. `GET /cvs/{cvId}/ats-check` retrieves the latest result. See `05-openapi.yaml` for the added paths and schemas.

## 2. Multi-job-post comparison and coverage-gap reporting (build now)

### The gap this closes
The whole system is built one-CV-to-one-job-post at a time. A real job search isn't that — it's 10 to 30 applications, often to similar roles, run over weeks. The matching engine (Phase 3) already computes, for every application, exactly which requirements are supported, partial, unsupported, contradictory, or unclear (`03-data-model.md`, `match_evidence_items`). That data currently gets used once per application and then sits unaggregated. The missed opportunity: if a user runs their CV against eight similar job posts and six of them require a specific certification their CV doesn't show, that's a much stronger, more actionable signal than any single match result — and the system already has all the data needed to say so.

### What it does
A user groups job posts into a `job_post_collections` (e.g. "Senior Backend Roles — Q3"). Triggering a coverage report runs (or reuses, if already run) a `match_run` for each job post in the collection against a chosen CV profile version, then aggregates: which specific requirements recur across multiple posts with `unsupported`/`contradictory`/`unclear` support, ranked by how many posts in the collection share that gap. The output isn't a new kind of analysis — it's a ranking and grouping step over existing `match_evidence_items` rows.

Example of the shape of `coverage_reports.aggregate_gaps`:
```json
[
  {
    "requirement_text_cluster": "Kubernetes / container orchestration experience",
    "recurrence_count": 6,
    "recurrence_ratio": 0.75,
    "affected_job_post_ids": ["...", "..."],
    "current_support_level_distribution": { "unsupported": 5, "unclear": 1 }
  }
]
```
`requirement_text_cluster` implies some light normalisation across differently-worded requirements that mean the same thing (e.g. "Kubernetes experience" and "container orchestration (K8s)") — this is worth flagging honestly as the one place in this feature with real design difficulty, since naive exact-text matching would badly undercount recurrence, and full semantic clustering is its own scoped piece of work, not a one-line addition. Start with a simpler normalisation (case-folding, stemming, a small synonym list for common tech/skill terms) and treat true semantic clustering as a later refinement once real data shows how much it's needed.

### Design note: why this is low-risk despite being new tables
No new AI generation, no new evidence-binding logic, no new fabrication surface. It's a read/aggregation model over `match_runs` and `match_evidence_items`, both already built in Phase 3. The main engineering cost is the requirement-clustering step above, which is bounded and can ship in a simpler form first.

### Phase placement
Natural fit is a Phase 3 addendum or an early Phase 5 item — it depends on the matching engine existing (Phase 3) but has no dependency on generation (Phase 3's CV drafting) or the cover letter workflow (Phase 4), so it can be built any time after Phase 3's matching engine lands without blocking or being blocked by Phase 4.

### New endpoints
`POST /job-post-collections`, `GET /job-post-collections`, `POST /job-post-collections/{collectionId}/coverage-report` (`202`, async per the existing pattern), `GET /coverage-reports/{reportId}`. See `05-openapi.yaml`.

## 3. Confidence-calibrated "fix before you apply" checklist (build now)

### The gap this closes
Today the system generates a tailored CV and stops. But the richest, most specific feedback the system could give a user — "your leadership bullet is qualitative, job posts at this level expect a number" or "your cloud experience claim has `unclear` support because this CV section extracted with low confidence, check the formatting" — is sitting unused in `match_evidence_items` the moment matching completes. This is the cheapest of the six ideas to build, because it needs no new data collection and no new AI generation call: it's a synthesis pass over data the system already computed in Phase 3.

### What it does
When a `tailored_cv_drafts` row is generated, populate `improvement_checklist` (new column, see `03-data-model.md`) by walking the `match_evidence_items` for the underlying `match_run` and surfacing anything not `supported`:

```json
[
  {
    "requirement_text": "Team leadership experience",
    "support_level": "partially_supported",
    "suggestion": "Your CV mentions leading a team but doesn't quantify size or outcome. Consider adding a specific number if you have one.",
    "priority": "high"
  },
  {
    "requirement_text": "Terraform experience",
    "support_level": "unsupported",
    "suggestion": "No evidence of Terraform found. If you have relevant experience not currently on your CV, add it before reapplying, or address it directly in your cover letter.",
    "priority": "medium"
  }
]
```

`priority` is a simple heuristic (required-vs-preferred requirement type, weighted by support level — `unsupported` on a `required` requirement ranks highest) rather than a new model judgment call, for the same reason as extension #1: keep judgment-light, deterministic steps deterministic, and reserve LLM calls for genuinely judgment-requiring tasks.

### Design note: this is the one place "helpful" and "fabrication risk" are closest together — handle carefully
The suggestion text itself is generated content shown to the user, even though it's not part of the CV or cover letter. It needs the same discipline as any other generated text: it should describe the *gap*, never invent a plausible-sounding fix that implies the user has experience they don't ("consider mentioning your Terraform migration project" when no such project exists anywhere in their CV is exactly the kind of fabrication this whole pack exists to prevent, just relocated to a different UI surface). The safest implementation is template-based suggestion text keyed off `support_level` and `requirement_type` (as the two examples above are), not a free-form LLM call per checklist item — if a future version wants richer, more specific suggestion text, that upgrade needs the same schema validation and evidence-binding discipline as tailored CV generation, not an exemption because it "isn't really the CV."

### Phase placement
Phase 3, as part of the tailored CV generation task — it's populated at the same time as the draft, from data the same generation step already has in hand.

### API surface
No new endpoint needed — `improvement_checklist` is simply a new field on the existing `GET /tailored-cvs/{draftId}` response. See `05-openapi.yaml`.

## 4. Master CV concept (schema extension now, feature build later)

### The gap this closes
The current model treats each CV upload as independent — its own `cv_files` row, its own version lineage via `cv_profile_versions`. A serious job seeker doesn't work this way: they maintain one evolving "master" CV and want every past and future tailored draft to trace back to it, and ideally to regenerate cleanly when the master improves (e.g. after acting on extension #3's checklist). Today, if a user fixes their master CV, there's no way to say "refresh my three active tailored drafts from this improved base" — each `tailored_cv_drafts` row is only reachable via one specific `match_run`, pinned to one specific `cv_profile_version_id`, with no concept of "these are all downstream of the same underlying document as it evolves."

### What's added now versus later
Only the schema seam is added in this pass: `cv_profile_versions.master_profile_id`, a nullable self-referencing-in-spirit column pointing to the profile version this one was derived from as a base (see `03-data-model.md`). This is deliberately *not* the same relationship as `version_number` (which tracks re-parsing the same uploaded file) — `master_profile_id` tracks "the user edited/improved their CV and re-uploaded, and this new version is a conceptual descendant of that one," which can span different `cv_files` rows entirely (a new upload, not a reprocess of the old one).

Building the actual feature — a "regenerate all downstream drafts" action, a UI concept of "your master CV," lineage visualization — is future work, deliberately scoped out of this pass. The reason to add the column now rather than later: retrofitting a lineage concept onto profile versions after `match_runs` and `tailored_cv_drafts` already exist in production, with real data that has no lineage recorded, is a much harder migration than reserving the column from the start and leaving it nullable/unused until the feature is actually built.

## 5. Match-quality feedback signal (schema extension now, feature build later)

### The gap this closes
Once the matching engine (Phase 3) is live, there's currently no way to know if it's actually accurate. If a user's CV clearly supports a requirement but the engine returns `unsupported`, nothing captures that disagreement — the user just gets a worse experience with no feedback loop for the team to notice a systematic problem (a bad prompt, a heuristic that's too strict, a recurring parsing gap).

### What's added now versus later
`match_evidence_items.user_feedback` (nullable JSONB, see `03-data-model.md`), populated only when a user explicitly disputes a match result — never inferred, never defaulted, never treated as new evidence for generation purposes on its own (a user saying "actually I do have this" doesn't make it `supported`; the underlying CV or job post data has to actually change, or the disagreement stays flagged as feedback rather than fact — this boundary matters precisely because loosening it would be a backdoor around the non-fabrication rule).

Building the feature — a UI affordance for flagging a match result, an internal dashboard for reviewing disputed matches, any process for actually using this signal to improve the matching prompts/heuristics — is future work. The column is added now for the same reason as #4: cheap to reserve, expensive to retrofit onto live data later.

## 6. Career-changer transferable-skill matching (flag for a separate decision — do not build without one)

### The idea
Everything in the matching engine as designed evaluates direct evidence: does the CV show experience that satisfies this requirement. A career changer's real question is different and harder: "which of my skills, even from an unrelated field, plausibly transfer to this requirement I have no direct experience in." A project manager moving into product management, or a teacher moving into corporate training, has real transferable skills that a direct-evidence matcher will mostly score as `unsupported` — technically correct by the current definition, but not useful to that user.

### Why this needs a separate conversation before any design work
This is structurally different from every other extension in this document, including the ones with real design difficulty (like #2's requirement clustering). Direct-evidence matching, however imperfect, has a checkable ground truth: does the text say this, yes or no. Transferable-skill matching requires the system to make an inferential leap — "experience A is *similar enough* to requirement B to be worth mentioning" — that has no clean ground truth and is exactly the kind of reasoning most prone to producing a claim that sounds plausible but oversells the connection. Done well, this could be a genuine differentiator for an underserved and often-anxious user group. Done carelessly, it's the most direct route to violating this entire pack's central design constraint (`02-architecture-overview.md` §1: never invent experience, never round up).

If this gets greenlit, it should be designed with at least these guardrails, decided deliberately rather than defaulted into:
- Transferable-skill claims must be visually and structurally distinct in the UI from direct-evidence claims — never rendered as if they were the same kind of match.
- The generated language must make the inferential nature of the claim explicit ("your experience in X may be relevant to Y" is a fundamentally different claim than "your CV shows Y"), not softened into something that reads as direct evidence on a skim.
- This is very likely a new, distinct `support_level` value (something like `transferable`, sitting conceptually apart from the existing five), not a stretch of `partially_supported` — conflating "same field, incomplete evidence" with "different field, analogous evidence" would blur two things that need different generated language and different user-facing framing.

None of this is designed further here on purpose. This section exists to make sure the idea doesn't get quietly implemented as a variant of `partially_supported` by someone moving fast in Phase 3 or 4 — it needs its own scoping conversation, informed by this pack's non-fabrication discipline, before any schema or prompt work starts.
